**ライフプランシミュレータ 要求仕様**

本書は要求のみを記述する。**実現方法は書かない。**個々の作業項目は GitHub の issue にある。

移行期にのみ必要な事柄（Google Sheets 版との等価性の確認など）は要求ではないため本書に含めない。

機能要求はイベント列の性質として記述し、次の 2 種に分類する。

- **安全性**: こういうイベント列は含まれない（悪いことが起きない）
- **活性**: こういうイベント列は拒否されない（良いことが可能である）
  ※ Alpern & Schneider の活性の定義ではない

**イベントの語彙**

| 記号 | イベント |
|:--|:--|
| `edit(T)` | 人間が入力テーブル `T` を編集する |
| `edit(P)` | 人間がプロジェクトファイル `P` を編集する |
| `edit(L)` | 人間が制度テーブル `L` を編集する |
| `run(c)` | 変換コマンド `c` を実行する |
| `emit(T)` | テーブル `T` が出力される |
| `chart(T)` | テーブル `T` からグラフが出力される |
| `compare(P₁, P₂)` | プロジェクト `P₁` と `P₂` を比較する |
| `verify(v)` | 検証 `v` を実行する |
| `reject(r)` | 理由 `r` を報告して実行を拒否する |
| `observe(T)` | 人間がテーブル `T` を読む |

---

# LP-FREQ-01: 入力テーブルに記入し、資産の時間的推移を確認できる

分類: **活性** および 写像の性質としての **安全性**

**活性**

`edit(入力テーブル)` → `run(...)` → `emit(assets)` → `observe(assets)` → `chart(assets)`
の列は拒否されない。人間が Google Sheets を開くことなく、
テキストエディタと CLI だけでこの列を完了できる。

**写像の性質**

本要求は、入力テーブルから `assets`（およびそのグラフ）への写像を定める。
この写像は以下を満たす。

1. **税・社会保険料を反映する。**
   所得税・住民税・固定資産税、および健康保険・介護保険・厚生年金・国民年金・雇用保険・
   後期高齢者医療の保険料が `assets` に反映される。
   資産推移は手取りベースであり、税を無視した推移には意味がないため。

2. **税・社会保険料を過小に写さない。**（安全性）
   計算された税額・社会保険料が実績帳票（LP-FREQ-10）の対応する値を下回るにもかかわらず、
   その事実が報告されないまま `emit(assets)` に至るイベント列は含まれない。

   **これは本書で最も強い制約である。** Google Sheets 版には税を過小に計算する誤りがあり、
   その結果として過大な支出を許す計画が承認された。同種の誤りは家計の破綻に直結する。

   誤差は対称に扱わない。過大な見積もりは保守的な計画を生むだけだが、
   過小な見積もりは破綻を生む。

# LP-FREQ-02: 中間テーブルを個別に確認できる

分類: **活性**

`run(...)` → `observe(中間テーブル)` の列は拒否されない。

LP-FREQ-01 の写像は、最終結果に至るまでの中間テーブル群として観測可能でなければならない。
「なぜこの年の資産がこの額になるのか」を、実装を読まずに追える必要がある。

中間テーブルは人間が読める形式であり、既存のツール（`tw` など）で観測できる。
専用のビューアは要求に含まれない。

# LP-FREQ-03: 任意の変換を単体で実行できる

分類: **活性**

任意の変換 `c` について、`c` の入力テーブルが存在する状態から
`run(c)` → `emit(cの出力テーブル)` の列は拒否されない。

`c` の前後の変換を実行することを強制されない。
差分調査のたびに全体を再計算させられると、原因の切り分けができないため。

# LP-FREQ-04: 複数のプロジェクトを定義して横断比較できる

分類: **活性**

`edit(P₁)` → `edit(P₂)` → `run(...)` → `compare(P₁, P₂)` → `observe(比較結果)`
の列は拒否されない。

プロジェクトとは「1 組の入力テーブルの選択」である。
入力テーブルは次の 3 種に分類され、プロジェクトはそのいずれをも差し替えうる。

| 種別 | 内容 | 例 |
|:--|:--|:--|
| **入力** | 人間が選べるもの | 就労、一括返済の有無、進学先、生活費 |
| **環境** | 人間が選べないもの | 運用利率、金融危機の発生年と下落率、インフレ率 |
| **実績** | 起きたこと。**選べないが、環境でもない** | 各行の年末残高、収支明細 |

**実績を環境に含めない。**過去は変えられないという点で人間が選べるものではないが、
環境パラメータが「起こりうることの見込み」であるのに対し、実績は「起きたこと」で
あって見込みではない。同じ列に置くと、実績を差し替えた比較が「環境が違う計画の
比較」に読める。**プロジェクトが選ぶのは実績の内容ではなく、どの時点までの実績を
参照するか——すなわち起点——である**（LP-FREQ-23）。

**比較の機構はプロジェクト横断比較ただ 1 つである。**
環境パラメータのために別の機構（出力テーブルに候補ごとの列や行を持たせるなど）を設けない。

理由は 2 つ。第一に、機構を分けると環境パラメータを含むテーブルだけが
「年以外のキーを持つ」特異な形になり、比較・描画・検証のすべてに例外が生じる。
第二に、機構を分ける設計は「環境パラメータは計算の最終段にしか影響しない」という
性質に依存するが、この性質は恒久的ではない
（例: 金融資産の運用益に課税を導入すると、利率が税計算に還流する）。
プロジェクトに統一する設計はこの性質に依存しない。

# LP-FREQ-05: プロジェクト間で入力テーブルを共有できる

分類: **活性**

複数のプロジェクトが同一の入力テーブルを参照する構成は拒否されない。

# LP-FREQ-06: プロジェクト間で入力テーブルが暗黙に複製されることはない

分類: **安全性**

`edit(P₁)` に続いて、人間が明示的に複製を指示していないにもかかわらず
`P₁` の入力テーブルの複製が生成されるイベントは含まれない。

複製されると、前提を更新したときに片方だけに反映され、
比較結果が「前提の違い」ではなく「更新漏れ」を映すことになるため。

# LP-FREQ-07: 中間テーブルもプロジェクト間で比較できる

分類: **活性**

`compare(P₁, P₂)` は最終テーブルだけでなく、任意の中間テーブルに対しても拒否されない。

「なぜこの年の資産が違うのか」の追跡には最終値の比較では足りないため。

# LP-FREQ-08: プロジェクト間の差が入力・環境・実績のどれに由来するか判別できる

分類: **活性**

`compare(P₁, P₂)` → `observe(比較結果)` において、
`P₁` と `P₂` で異なる入力テーブルがどれであるか、
およびそれが LP-FREQ-04 の 3 種のどれかを観測できる。

LP-FREQ-04 で比較の機構を 1 つに統一した結果、
「この差は自分の決定によるものか、環境によるものか、起点の違いによるものか」が
比較結果から自明でなくなる。この区別は意思決定にとって本質的であるため、
要求として明示する。

すなわち `compare(base, wife-fulltime)`（入力のみが異なる）と
`compare(base, base-crisis)`（環境のみが異なる）と
`compare(base, as-of-2022)`（実績のみが異なる）と
`compare(base, wife-fulltime-crisis)`（複数が異なる）を、
比較結果を見た人間が取り違えない。

**分類できない入力テーブルは「不明」と書き、どれかに寄せない。**選べないものが
選べるものの中に混じれば、この区別を設けた意味がそこで失われる。

# LP-FREQ-09: 資産推移をグラフとして出力できる

分類: **活性**

`emit(assets)` → `chart(assets)` の列は拒否されない。
グラフは LP-FREQ-04 の複数プロジェクトを重ねて表示できる。

# LP-FREQ-10: 実績帳票と計算結果を突合できる

分類: **活性**

`verify(実績突合)` → `observe(突合結果)` の列は拒否されない。

突合の対象となる実績帳票は、給与明細（月次）、e-Tax で作成した確定申告書（年次）、
源泉徴収票（年次）、家計簿の集計（月次）である。
**帳票そのものは公開しない。**

本要求は LP-FREQ-01 の「税・社会保険料を過小に写さない」の判定根拠を与える。

# LP-FREQ-11: 制度テーブルの出典を辿れる

分類: **活性**

任意の制度テーブルの値について、`observe(制度テーブル)` から
その値の根拠（法令・自治体・保険者の一次情報）に到達できる。

制度は改正される。改正時に「この値はどこから来たか」を辿れないと、
更新すべき値を特定できないため。

# LP-FREQ-12: インフレ率を考慮した推移を得られる

分類: **活性**

`edit(インフレ率)` → `run(...)` → `emit(assets)` の列は拒否されない。

インフレ率は環境パラメータであるため、その違いによる比較は
LP-FREQ-04 のプロジェクト横断比較で行う。本要求が追加で求めるのは、
インフレ率が実際に計算に適用されること（費目ごとの適用可否を含む）である。

本要求は第2ステップで充足する（移行期の都合により後回しにする）。

# LP-FREQ-13: 検証に失敗した状態で、失敗が隠されたまま結果が確定することはない

分類: **安全性**

検証項目 `v` が失敗しているにもかかわらず、`verify(v)` の失敗が
報告されないまま `emit(assets)` に至るイベント列は含まれない。

既知の乖離は「既知である」ことを明示した上で残してよい。
ただし黙って通すこと、許容誤差を広げて通すことは含まれない。

# LP-FREQ-14: 入力テーブルに誤りがあるまま結果テーブルが出力されることはない

分類: **安全性**

入力テーブルが不整合（欠損年、重複、範囲外の値、単位の不一致、参照先の不在）を
含む状態で `emit(assets)` に至るイベント列は含まれない。

不整合な入力から出た数字は、正しく見えるがゆえに危険である。

# LP-FREQ-15: 誤りの報告が 1 件ずつに分割されることはない

分類: **活性**

入力テーブルに `n` 件の誤りがあるとき、`run(...)` → `reject(r₁, r₂, ..., rₙ)` の列は拒否されない。

すなわち、`reject(r₁)` → `edit` → `reject(r₂)` → `edit` → ... という
1 件ずつの往復を強制されない。

# LP-FREQ-16: 同じ入力から異なる出力が得られることはない

分類: **安全性**

同一の入力テーブル・制度テーブル・プロジェクトファイルに対する 2 回の `run(c)` が、
異なる `emit(T)` を生じるイベント列は含まれない。

実行時刻・乱数・ネットワーク・環境変数・カレントディレクトリに依存しない。

決定性がなければ、差分が「前提を変えたから」なのか「たまたま」なのかを区別できない。

# LP-FREQ-17: 古い中間テーブルが結果に混入することはない

分類: **安全性**

入力テーブル `T` が `edit(T)` された後、`T` に（推移的に）依存する中間テーブルが
再計算されないまま `emit(assets)` に用いられるイベント列は含まれない。

一部だけが更新された中間テーブル群から得た資産推移は、
どの前提にも対応しない架空の計画である。

# LP-FREQ-18: 異常終了したコマンドが不完全な出力を残すことはない

分類: **安全性**

`run(c)` が失敗したにもかかわらず、`c` の出力テーブルが部分的に書き込まれた状態で
残るイベント列は含まれない。

部分的な出力は LP-FREQ-17 の混入を引き起こす。

# LP-FREQ-19: 制度が定めるもの以外の丸めが計算過程に入ることはない

分類: **安全性**

制度が定める丸め（課税所得の 1,000 円未満切捨て、所得税額の 100 円未満切捨て、
標準報酬月額の等級判定、各種上限額の適用）以外の丸めが計算過程に入るイベント列は含まれない。

万円単位の小数で計算すると制度上の丸めを表現できず、かつ独自の丸め誤差を累積させる。
これは LP-FREQ-01 の「税・社会保険料を過小に写さない」を破る経路の 1 つである。

# LP-FREQ-20: 入力テーブルが暗黙に書き換えられることはない

分類: **安全性**

人間が `edit` を指示していないにもかかわらず、入力テーブル・制度テーブル・
プロジェクトファイルが変更されるイベントは含まれない。

生成されたテーブルと人間が管理するテーブルの区別が失われると、
「誰がこの前提を決めたか」が追えなくなる。

# LP-FREQ-21: 結果を出す前に入力テーブルを検査でき、未完成でも部分的に検査できる

分類: **活性** および **安全性**

**活性**

`edit(T₁)` → `run(検査)` → `observe(検査結果)` の列は、
他の入力テーブル `T₂ … Tₙ` が存在しない、あるいは書きかけであっても拒否されない。

**検査すべき不変条件は、存在する入力テーブルから自動的に定まる。**
各不変条件はその成立を確かめるのに必要な入力テーブルを持ち、
それが揃っているかどうかで実行可能性が決まる。人間が検査項目を数え上げる必要はない。

入力テーブルが欠けている状態を許すかどうかだけを指定する。

- 既定では、入力テーブルの欠落は誤りとして報告される
- 欠落を許す指定をしたときは、確かめられない不変条件を飛ばして残りを検査する

入力テーブルを書く作業は一度に終わらない。
1 つ書いた時点で誤りを知れることは、全部書き終えるまで何も分からないことより望ましい。
また、`emit` に到達できない状態でも検査だけは走らせられる必要がある。

**安全性**

飛ばされた不変条件がある検査の結果が、全体の検査の結果として扱われるイベント列は含まれない。

- 検査は、**飛ばした不変条件を名前で報告する**
- 飛ばされた不変条件がある検査の成功は、
  LP-FREQ-14 が要求する「入力テーブルに誤りがない」を満たさない

一部の不変条件（すべての年キーのテーブルが同じ年の範囲を覆う、
プロジェクトファイルの参照先が存在する、など）は、
入力テーブルが揃っていなければ確かめられない。
未検査を「成功」とだけ報告すると、検証されていないものが検証済みに見える。
**これは本書が排除しようとしている誤った確信そのものである**（LP-FREQ-13 と同じ性質）。

なお検査は誤りを一度にまとめて報告する（LP-FREQ-15）。これは検査範囲によらない。

# LP-FREQ-22: 実績の資産額推移を取り込み、計画と重ねて確認できる

分類: **活性** および **安全性**

**活性**

`edit(実績テーブル)` → `run(比較)` → `chart(...)` → `observe(グラフ)` の列は拒否されない。

グラフ上で、計画による資産推移と実績の資産額推移が重ねて表示される。
これにより、未知の出費などによって計画と現実が乖離していることに気付ける。

- 実績テーブルは**口座種別の分解能を持つ**（銀行預金、投資信託など）。
  計画側は資産を貯蓄と金融資産に分けて扱うため、実績が合計値のみでは同種のものを比較できない。
- 家計簿サービス（MoneyForward）が出力する CSV から実績テーブルを作れる。

**安全性**

1. **実績の違いが意思決定の違いに見えることはない。**
   同一の実績テーブルを参照する 2 つのプロジェクトの比較結果は、
   実績の内容によらず、入力パラメータと環境パラメータの差のみを映す。

   実績はどの計画を評価する場合でも同一であり、プロジェクトごとに複製すると
   プロジェクト間比較の雑音になる（LP-FREQ-06、LP-FREQ-07）。

2. **実績が増えたことで、過去を振り返る手段が失われることはない。**
   実績テーブルに行が追加されたとき、
   それ以前の時点を起点とする計画を得る手段が失われるイベント列は含まれない。

   **これは本要求の目的そのものを守る制約である。**
   起点を常に最新の実績に置くと、過去に生じた乖離が吸収されて見えなくなる。
   乖離を観測するには、過去のある時点を起点とした計画を構成できなければならない。

3. **実績と計画が区別できない形で提示されることはない。**
   グラフおよびテーブルにおいて、どの系列が実績でどの系列が計画かを観測できる。

# LP-FREQ-23: 計画の起点は実績テーブルの最終行である

分類: **活性** および **安全性**

**活性**

資産推移の計算の起点は、そのプロジェクトが参照する実績テーブルの最終行の残高である。

- `edit(実績テーブル に行を追加)` → `run(...)` → `emit(assets)` の列は拒否されない。
  **実績の行を足すだけで起点が更新される。**再計画のための操作を別途必要としない
- 参照する実績テーブルはプロジェクトが選ぶ。
  過去のある時点までの実績を参照するプロジェクトを作れば、その時点が起点になる

計画と実績が乖離し始めたとき、「これからどうするか」を決めるには
現在の資産額を起点にした比較が要る。
過去の計画に基づく資産額のままでは、**未来の選択肢の比較に過去の乖離が雑音として混入する**。

**起点は資産推移の初期値であり、収入・支出・税の計算には影響しない。**
これらは起点によらず全期間について計算される（LP-FREQ-10 の突合を成立させるため）。

同じ問いに対する 2 通りの構成:

| 問い | 参照する実績 | 起点 |
|:--|:--|:--|
| これからどうするか | 最新まで | 最新の実績 |
| 過去の計画は妥当だったか | 過去のある時点まで | その時点。以降は計画として計算され、実績と重ねられる |

**安全性**

1. **プロジェクトの起点を観測できる。**
   どの実績テーブルのどの時点を起点としたかを観測できる。

2. **起点の異なるプロジェクトを比較したとき、その事実が報告される。**
   起点が異なれば資産額の水準そのものが異なるため、
   差の大半が意思決定ではなく起点の差に由来する。
   これを黙って並べると、**起点の差が計画の優劣であるかのように見える**。
   LP-FREQ-08 が入力・環境・実績を区別させるのと同じ理由による。

# LP-FREQ-24: プロジェクトファイルは他のプロジェクトを継承できる

分類: **活性** および **安全性**

**活性**

プロジェクトファイル `P′` が `P` を継承し、`P` と異なる slot だけを記述する構成は拒否されない。
継承せず、すべての slot を明示的に記述する構成も拒否されない。
**継承は使ってもよいし、使わなくてもよい。**

入力パラメータと環境パラメータは直交するため（LP-FREQ-04）、
プロジェクトは実質的にその直積になりうる。
すべての slot を毎回書くと、共通部分の更新が全プロジェクトに波及して漏れが生じる。

**安全性**

継承の結果として実際に使われる入力テーブルの集合を観測できる。

継承は「このプロジェクトが実際に何を使っているか」を読んで分からなくする。
解決後の姿を観測できなければ、比較結果の解釈を誤る。

# LP-FREQ-25: 設定は既定値・プロジェクト・コマンド引数の順に上書きされる

分類: **活性** および **安全性**

**活性**

プロジェクトファイルで指定できるものは、コマンド引数で上書きできる。
優先順位は次のとおりで、後にあるものが優先される。

1. 既定値
2. プロジェクトファイル（LP-FREQ-24 の継承を解決した後の値）
3. コマンド引数

プロジェクトファイルを編集せずに 1 つの値だけ変えて試せることは、
比較したい仮説を思いついてから結果を見るまでの距離を縮める。

**安全性**

有効になった値と、**その値がどこから来たか**を観測できる。

上書きの連鎖は、値の出所を不透明にする。
どの層で決まった値なのかを観測できなければ、
「プロジェクトファイルを直したのに結果が変わらない」を追跡できない。
